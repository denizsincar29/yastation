# yastation

Неофициальный клиент для управления Яндекс Станцией (Алисой) с
компьютера или сервера: озвучить текст, отправить голосовую команду,
поставить таймер/будильник, дёрнуть сценарий умного дома, запланировать
команды на потом. Не связан с Яндексом и не аффилирован с ним.

**Возможности:**
- REPL и одноразовый запуск команд из shell (cron/systemd timer/алиасы)
- HTTP-бэкенд — управляй колонкой с сервера из любой программы
- Тот же HTTP-бэкенд отвечает и по MCP (`/mcp`) — чтобы ИИшки (Claude и
  любые другие MCP-клиенты) сами дёргали Алису как инструмент, плюс
  отдельный локальный `-stdio` режим для Claude Desktop
- Быстрый локальный путь (Glagol WebSocket в локальной сети) с
  автоматическим fallback на облако, если локалка недоступна
- Планировщик (`/every`, `/at`) и скрипты (`/execute файл.txt`)
- Асинхронная очередь команд — не ждёшь round-trip к Яндексу на каждый ввод
- Свои команды с параметрами через конфиг (см. `examples/commands.json`)

**Нужен Go 1.25+** (у REPL самого по себе была бы достаточно и 1.23 —
единственная его внешняя зависимость это `github.com/coder/websocket`
для быстрого локального протокола Glagol, — но `cmd/yastation-server`
тянет ещё и официальный `github.com/modelcontextprotocol/go-sdk` для
MCP, которому нужен 1.25, так что этим требованием теперь живёт весь
модуль).

Официального API у Яндекса для этого нет. Общее понимание протокола
взято из нескольких открытых репозиториев про Яндекс Станцию; сама
реализация написана на Go самостоятельно. Подробности и что именно
проверено на реальном аккаунте — в `PROTOCOL_NOTES.md`. Протокол
недокументирован и может измениться в любой момент без предупреждения.

## Структура

```
cmd/
  yastation/            интерактивный REPL + одноразовый запуск команд из shell
  yastation-auth/       разовая QR-авторизация
  yastation-server/     HTTP-бэкенд (REST + MCP на /mcp) — управляй колонкой с сервера или из ИИ; -stdio — локальный MCP для Claude Desktop
internal/
  quasar/                библиотека протокола: сессия, устройства, сценарии, команды
  glagol/                 локальный WebSocket-протокол (быстрый путь, см. ниже)
  queue/                   асинхронная очередь: Enqueue возвращает мгновенно, воркер шлёт по одной по порядку
  scheduler/               /every и /at — периодические и разовые задачи
  dispatch/                 лёгкий диспетчер команд ("/имя аргументы", свой, не func_parser)
  app/                       склеивает всё выше в общий набор команд, разделяемый REPL и HTTP-сервером
examples/
  morning.txt             пример скрипта для /execute
```

## Установка и первый запуск

```bash
go build ./...          # или go run ./cmd/... по отдельности
go run ./cmd/yastation-auth   # один раз: логин по QR-коду
go run ./cmd/yastation         # интерактивный REPL
```

Токены сохраняются в `$YASTATION_TOKEN_FILE` (если задано) или
`<user config dir>/yastation/tokens.json` (на Linux — `~/.config/yastation/tokens.json`)
— не публикуй и не коммить этот файл.

## Одноразовый запуск из командной строки

Не обязательно сидеть в REPL — можно вызвать одну или несколько команд
прямо из shell (удобно для cron, systemd timer, алиасов):

```bash
yastation "привет с компа"                      # одна фраза, потом выход
yastation -c "volume 3" -c "say доброе утро"     # несколько команд подряд
yastation -e examples/morning.txt                 # то же, что -c "execute ..."
yastation -c "every 30m /say вода" -i             # запланировать и остаться в REPL
```

`-c` понимает значение как "команда [аргументы]" — ведущий `/` перед
именем команды добавляется сам, если его не написать (и не мешает, если
написать). Это специально: Git Bash переписывает аргумент, целиком
похожий на абсолютный юникс-путь, в путь Windows ещё до того, как Go его
увидит — `yastation -c "/pause"` там превращается в
`yastation -c "C:\Program Files\Git\pause"`. Пиши `-c "pause"` — и
работает одинаково что в git bash, что в cmd/PowerShell. Вложенный
`/say` внутри аргумента `/every` выше это не затрагивает — тот `/`
разбирает уже сам `/every`, а не эта авто-подстановка.

Если readline в твоём терминале глючит (например git bash) — `-noreadline`
или `YASTATION_NO_READLINE=1` переключает REPL на обычный построчный ввод
без истории/tab, но зато без сюрпризов.

Код возврата процесса — `1`, если хоть одна из команд упала с ошибкой (для
скриптов/cron), `0` если всё прошло гладко.

## Быстрый путь: локальный Glagol вместо облака

По умолчанию команды идут через облако Яндекса (создать/поправить
служебный сценарий, потом дёрнуть его) — это надёжно работает из любой
сети, но занимает ~1-2 секунды на команду. Если комп и колонка в одной
локальной сети, можно включить прямое WebSocket-подключение к колонке
(Glagol) — обычно это заметно быстрее.

Нужен только IP:порт колонки в локальной сети (у Яндекса нет надёжного
способа найти его без mDNS-библиотеки, поэтому просто задай вручную —
посмотри в списке DHCP-клиентов роутера или в приложении Дом с Алисой):

```bash
export YASTATION_GLAGOL_HOSTS="abc123deviceid=192.168.1.42:1961"
# несколько колонок через запятую:
# YASTATION_GLAGOL_HOSTS="dev1=192.168.1.42:1961,dev2=192.168.1.43:1961"
```

Device id колонки видно в выводе `/stations`. Если хост для устройства не
задан или подключение/отправка не удались — команда автоматически
падает обратно на облачный путь, ничего вручную переключать не надо.
Учти: у Glagol в этой реализации только один вид команды (`sendText`, как
если бы фразу произнесли голосом) — TTS-режим `/say` через Glagol технически
шлётся так же, как `/cmd`, разницы между ними локально нет (см.
`PROTOCOL_NOTES.md`).

## REPL

```
> привет с компа!               # просто текст -> озвучивается станцией
> - какая погода                  # дефис-пробел -> голосовая команда (алиас /cmd)
> /volume 3                      # громкость 0..10
> /say выключи свет
> /ask чё делаешь                 # алиас /cmd — ответ прозвучит из колонки, не в терминал
> /notify задача выполнена volume=4
> /timer 10 проверить духовку
> /alarm 7:30
> /reminder завтра купить хлеб
> /play  /pause  /stop  /next  /prev
> /weather
> /news
> /scenarios
> /scenario Вечер
> /stations                       # диагностика
> /every 30m /say выпей воды        # периодическая команда: s/m/h
> /at 7:30 /say доброе утро          # разовая команда в HH:MM
> /schedules
> /unschedule_all
> /execute examples/morning.txt      # прогнать скрипт построчно
> /help
```

Чтобы указать конкретную колонку вместо той, что задана переменными
окружения по умолчанию, добавь `station=Имя` в любое место аргументов:
`/say station=Кухня привет`.

## Асинхронность и очередь команд

Каждая команда станции — это несколько HTTP-запросов к Яндексу (создать
или поправить сценарий, затем дёрнуть его), и в сумме это может занимать
секунду-две. Чтобы не блокировать вызывающий код, `internal/queue`
устроен так:

- `App.Enqueue(line)` кладёт команду в очередь и **сразу возвращает
  управление**, ничего не дожидаясь. Ей пользуется REPL и планировщик —
  ты печатаешь следующую команду, не дожидаясь пока предыдущая долетит до
  колонки.
- Один воркер-горутина разбирает очередь строго по порядку, так что две
  команды, отправленные подряд, дойдут до колонки в том же порядке, а не
  наперегонки.
- `App.Execute(ctx, line)` — та же очередь, но ждёт реального результата
  и возвращает его вызывающему; этим пользуется HTTP-бэкенд, потому что
  HTTP-ответ должен нести реальный статус (успех/ошибка), но при этом
  конкурентные запросы всё равно не гонятся друг с другом за один и тот
  же сценарий колонки.

## HTTP-бэкенд (cmd/yastation-server)

Чтобы слать команды на Алису с сервера из любой программы (curl, другой
скрипт, вебхук и т.п.), а не только из интерактивного REPL — а заодно и
из ИИ через MCP (`/mcp` на том же порту, см. "MCP" ниже):

```bash
export YASTATION_HTTP_TOKEN=секрет   # опционально, но нужен если сервер смотрит наружу
go run ./cmd/yastation-server
```

По умолчанию слушает `:8737` (задаётся `YASTATION_HTTP_ADDR`) и работает
в BYOT-режиме: своего Яндекс-аккаунта у сервера нет, каждый запрос
обязан нести собственный `X-Yandex-Token` (см. раздел ниже). Никакой
`yastation-auth`/`tokens.json` для этого не нужно.

Если хочешь, чтобы сервер ещё и держал свой аккаунт — для запросов без
`X-Yandex-Token` — заведи его один раз (`go run ./cmd/yastation-auth`) и
запускай с `YASTATION_USE_DEFAULT_ACCOUNT=1`.

```bash
curl -X POST localhost:8737/command \
  -H "Authorization: Bearer $YASTATION_HTTP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"text": "привет с сервера"}'

curl -X POST localhost:8737/commands/volume \
  -H "Authorization: Bearer $YASTATION_HTTP_TOKEN" \
  -d '{"level": "3"}'

curl localhost:8737/schedules -H "Authorization: Bearer $YASTATION_HTTP_TOKEN"
curl localhost:8737/healthz   # без авторизации, для мониторинга
```

Тело запроса `/command` — простая форма для TTS/голосовой команды:
- `{"text": "привет", "station": "Кухня"}` — короткая форма, TTS;
- `{"text": "включи радио", "as_command": true}` — короткая форма, как
  голосовая команда (`/cmd`), а не TTS.

Для чего угодно посложнее (таймеры, сценарии, громкость, свои команды
из `commands.json` и т.д.) — используй `/commands/{name}` ниже, у каждой
команды свой URL со своими именованными полями.

Ответ: `{"ok": true, "output": "..."}` либо `{"ok": false, "error": "..."}`.

Каждый запрос ждёт реального выполнения (через ту же очередь, что и
REPL), так что можно сразу проверять `ok` в ответе.

### Эндпоинт на каждую команду: `/commands/{name}`

У каждой зарегистрированной команды — встроенной (`say`, `volume`,
`scenario`, ...) или из `config.json`/своего `commands.json` — есть свой
URL, авторегистрируемый при старте, с телом-JSON из её собственных
именованных полей. Никакой "строки как в REPL" тут нет и не парсится —
только явные поля:

```bash
curl localhost:8737/commands   # список всех команд + их полей (имя, тип, обязательность, station)
```

```bash
curl -X POST localhost:8737/commands/timer \
  -H "Authorization: Bearer $YASTATION_HTTP_TOKEN" \
  -d '{"minutes": "10", "label": "проверить духовку", "station": "Кухня"}'

curl -X POST localhost:8737/commands/say \
  -H "Authorization: Bearer $YASTATION_HTTP_TOKEN" \
  -d '{"text": "привет с сервера", "station": "Кухня"}'

curl -X POST localhost:8737/commands/scenario \
  -H "Authorization: Bearer $YASTATION_HTTP_TOKEN" \
  -d '{"name": "Вечер"}'
```

`GET /commands` покажет для каждой команды `"params": [{"name": "minutes",
"kind": "number", "optional": false}, ...]` и `"takes_station": true/false` —
ровно то, что нужно передать в теле. Неизвестное имя команды — `404`,
пропущенное обязательное поле — `400` с текстом, какое именно.

`station` — в теле (`"station": "..."`) или заголовком `X-Station`, если
команда вообще принимает станцию (`takes_station`). `X-Yandex-Token`/
список допуска работают одинаково на всех этих эндпоинтах.

### Bring your own token: управлять чужой станцией со своего сервера

Если хочешь со своего сервера слать команды не на свою колонку, а,
например, на мамину — не обязательно ставить туда весь проект и просить
маму что-то запускать. Передай её Yandex OAuth x-token прямо в запросе
заголовком `X-Yandex-Token`, и запрос выполнится от имени того аккаунта,
которому принадлежит токен, а не от имени того, что настроен на сервере —
**но только если этот аккаунт есть в списке допуска** (см. ниже), иначе
403 независимо от того, насколько токен валиден:

```bash
# сначала добавить мамин аккаунт в список допуска (один раз) —
# CLI откроет QR-ссылку, мама подтверждает вход на своём телефоне
go run ./cmd/yastation-access add Мама

# узнать id/имена станций на том аккаунте
curl localhost:8737/stations \
  -H "Authorization: Bearer $YASTATION_HTTP_TOKEN" \
  -H "X-Yandex-Token: <мамин x-token>"
# -> [{"id":"...","name":"Кухня","house_name":"Дом","platform":"yandexstation_2"}]

# затем команда на конкретную станцию по её id или имени
curl -X POST localhost:8737/command \
  -H "Authorization: Bearer $YASTATION_HTTP_TOKEN" \
  -H "X-Yandex-Token: <мамин x-token>" \
  -H "X-Station: Кухня" \
  -d '{"text": "мама, не забудь лекарство"}'
```

Станцию можно указать либо заголовком `X-Station`, либо полем `"station"`
в теле JSON — оба варианта равнозначны, `X-Station` просто удобнее, когда
не хочется трогать тело запроса.

#### Список допуска (`internal/access`, `cmd/yastation-access`)

`X-Yandex-Token` сам по себе не даёт доступа — сервер сначала узнаёт,
чей это аккаунт (`login.yandex.ru/info`, см. `quasar.WhoAmI`), и
проверяет его uid по списку в `access.json`
(`$YASTATION_ACCESS_FILE`, иначе `<user config dir>/yastation/access.json`).
Список пуст по умолчанию — свежий сервер никого не пускает в BYOT, пока
явно не добавишь:

```bash
go run ./cmd/yastation-access list                 # кто есть
go run ./cmd/yastation-access add [имя]            # добавить (QR-вход)
go run ./cmd/yastation-access remove <uid|логин|имя>  # отозвать
```

`add` использует тот же QR-вход, что и `yastation-auth`, но подтверждать
его не обязательно тебе — перешли ссылку тому, кому даёшь доступ, пусть
откроет и подтвердит на своём телефоне. Сам его OAuth-токен нигде не
сохраняется, в `access.json` попадают только имя и uid; он и дальше сам
приносит свой живой `X-Yandex-Token` на каждый запрос.

Отзыв (`remove`) действует немедленно, даже если у отозванного клиент
ещё "тёплый" в 20-минутном кэше сервера — список допуска перечитывается
на каждый запрос.

`Authorization: Bearer` (если задан `YASTATION_HTTP_TOKEN`) — это доступ
к твоему серверу вообще, отдельно от `X-Yandex-Token`/списка допуска,
которые выбирают **чей** аккаунт Яндекса дёргать и разрешено ли это
вообще. Про то, что такое x-token, откуда его взять и насколько это
вообще безопасная идея — раздел "Безопасность" ниже.

Клиенты для чужих токенов кэшируются в памяти 20 минут (не логируется и
не хранится сам токен — только его sha256 в качестве ключа кэша), чтобы
не проходить логин заново на каждый запрос.

### MCP: чтобы ИИшки могли болтать с Алисой

Тот же `yastation-server` (тот же бинарь, тот же порт `:8737`, тот же
`access.json`) отвечает ещё и на `/mcp` — по [MCP](https://modelcontextprotocol.io)
(Streamable HTTP), чтобы Claude или любой другой MCP-совместимый ИИ мог
дёргать Алису напрямую как инструмент, без curl и без REPL. Отдельного
сервера/порта поднимать не надо — `/mcp` просто ещё один роут рядом с
`/command`.

Авторизация **буквально та же самая**, что у `/command` (см. "Bring
your own token" выше) — то же самое правило выбора аккаунта
(`X-Yandex-Token` → список допуска, иначе аккаунт сервера по умолчанию,
если `YASTATION_USE_DEFAULT_ACCOUNT=1`, иначе 401), тот же кэш клиентов,
тот же `YASTATION_HTTP_TOKEN`:

- `X-Yandex-Token` — свой (или доверенного человека) Yandex OAuth-токен.
  Если не передан и у сервера есть свой аккаунт по умолчанию —
  используется он. Если не передан и своего аккаунта нет — `401`.
  Проверяется по списку допуска на каждый запрос, не только при
  подключении — отзыв (`yastation-access remove`) действует немедленно.
- `X-Station` — необязателен, станция по умолчанию для инструментов,
  если её не передать явно в аргументах вызова.

Без доступа — сразу чистый `401`/`403` с JSON-телом, ещё до входа в
MCP-протокол.

#### Инструменты

Каждая зарегистрированная команда (встроенная — `say`, `volume`,
`scenario`, `notify`... — или из `config.json`/своего `commands.json`)
становится своим MCP-инструментом `alice_<имя>` со своей JSON-схемой
параметров, сгенерированной прямо из диспетчера команд — список
инструментов и их описания смотри через `tools/list` любого MCP-клиента
(или `alice_help` ниже для текстового обзора разом). Никакого общего
"выполни строку как в REPL" эскейп-хэтча больше нет — у каждого
инструмента свои настоящие именованные поля.

Пара примеров того, что получится:

| Инструмент | Параметры |
|---|---|
| `alice_say` | `text` (обяз.), `station` (опц.) |
| `alice_cmd` | `text` (обяз.), `station` (опц.) |
| `alice_notify` | `text` (обяз.), `volume` (опц., число), `station` (опц.) |
| `alice_volume` | `level` (обяз., число), `station` (опц.) |
| `alice_scenario` | `name` (обяз.) |
| `alice_help` | без параметров — текстовый обзор всех команд разом |
| `alice_stations` | без параметров — список колонок на аккаунте |

**Важная особенность протокола:** у `alice_cmd` (и вообще у голосовых
команд) нет способа вернуть текстовый ответ Алисы — он прозвучит только
из динамика колонки, неофициальный протокол Яндекса этого не отдаёт (см.
`PROTOCOL_NOTES.md`). Инструмент лишь подтверждает, что команда
отправлена.

#### Получить x-token через браузер (`/auth/start`)

Чтобы не лезть в терминал каждый раз, когда нужен свежий x-token для
заголовка `X-Yandex-Token` (свой или для нового человека/клиента) —
открой `https://<твой-домен>/auth/start` в браузере. Это НЕ полноценный
OAuth (никакой MCP-клиент не подключится через это автоматически) —
просто обёртка для человека над тем же `quasar.LoginViaQR`, которым
пользуется `yastation-auth`:

1. `/auth/start` открывает вкладку с подтверждением входа в Яндексе
   (та же ссылка, что обычно превращают в QR) и сама переходит на
   `/auth/result?id=...`.
2. Подтверждаешь вход на стороне Яндекса.
3. `/auth/result` обновляется сама (без JS, `<meta refresh>`) и
   показывает x-token текстом для копирования, как только вход
   подтверждён.

Ничего не пишет на диск и не трогает `tokens.json`/`access.json`
сервера — только показывает токен один раз, в памяти процесса, и
забывает его сама через 10 минут. Если задан `YASTATION_HTTP_TOKEN` —
роуты `/auth/*` тоже под ним, но так как обычная навигация браузера не
умеет ставить заголовки, для них дополнительно принимается
`?token=...` в самом URL (например `/auth/start?token=секрет`) —
только для `/auth/*`, остальные эндпоинты как были, через заголовок.

#### Подключение как удалённый коннектор (HTTP)

Способ зависит от конкретного ИИ-клиента/хоста. Важно: заголовки
(`X-Yandex-Token`, при необходимости `Authorization: Bearer` для
`YASTATION_HTTP_TOKEN`) нужно прописать **в конфиге клиента статически** —
если оставить сервер без заголовков, многие MCP-клиенты (VS Code, Cursor
и т.п.) на первый же `403` попытаются сами угадать OAuth-эндпоинты
(`/authorize` и т.д.) на этом же домене по спеке MCP Authorization — а
у нас их нет, будет просто редирект в никуда. Сервер намеренно никогда
не отвечает `401`/`WWW-Authenticate` на `/mcp` — именно они сигнализируют
клиенту "начинай OAuth-дискавери"; здесь всегда `403` с обычным текстом
ошибки в JSON.

VS Code (`mcp.json`, `Ctrl+Shift+P` → `MCP: Open User Configuration`):

```json
{
  "servers": {
    "yastation": {
      "type": "http",
      "url": "https://<твой-домен>/mcp",
      "headers": {
        "X-Yandex-Token": "<свой x-token>",
        "X-Station": "Кухня"
      }
    }
  }
}
```

Пример для `claude mcp add`-подобной конфигурации:

```json
{
  "type": "streamable-http",
  "url": "https://<твой-домен>/mcp",
  "headers": {
    "X-Yandex-Token": "<свой x-token>",
    "X-Station": "Кухня"
  }
}
```

За Caddy на VPS — тот же поддомен/reverse proxy, что уже настроен для
`/command`, никакого отдельного порта. Учти: не все MCP-хосты умеют
слать произвольные заголовки прямо из json-конфига (например, ванильный
`claude_desktop_config.json` — нет, только через прокси вроде
`mcp-remote`); для Claude Desktop проще способ ниже.

Если токен протух или его отозвали — сервер отвечает `403` с текстом
вида «Токен недействителен. Переавторизуйся... / rerun the
authorization and change the header token» вместо попытки что-то
редиректить. Получил такой ответ — значит просто обнови значение
`X-Yandex-Token` в конфиге клиента на свежий (`go run ./cmd/yastation-auth`
+ актуальный x-token своего аккаунта) и переподключись.

#### Подключение локально (`-stdio`, Claude Desktop)

Флаг `-stdio` переключает `yastation-server` в совсем другой режим:
без HTTP вообще, без заголовков, без `access.json` — говорит MCP прямо
через stdin/stdout за один уже сохранённый локальный аккаунт (тот же
`tokens.json`, что у REPL). Это то, что умеет любой MCP-хост из коробки,
включая `claude_desktop_config.json` — если ещё не логинился, сначала
`go run ./cmd/yastation-auth`.

Собери бинарь и пропиши в `claude_desktop_config.json`
(`%APPDATA%\Claude\claude_desktop_config.json` на Windows):

```bash
go build -o yastation-server.exe ./cmd/yastation-server
```

```json
{
  "mcpServers": {
    "yastation": {
      "command": "C:\\Users\\denizsincar29\\files\\gos\\yastation\\yastation-server.exe",
      "args": ["-stdio"]
    }
  }
}
```

Текущая директория `command` не важна — путь к бинарю уже абсолютный,
а сам `yastation-server` ничего не читает по относительным путям (конфиг
команд и `tokens.json`/`access.json` резолвятся через `os.UserConfigDir()`,
т.е. от домашней папки пользователя, не от cwd процесса). `cwd` имело
бы значение, только если бы ты передавал относительный путь в
`YASTATION_COMMANDS_FILE` — тогда его лучше сделать абсолютным на
всякий случай.

Хочешь станцию по умолчанию не как в REPL, а конкретно для Desktop —
можно добавить `"env"` в этот же блок конфига:

```json
"env": { "YASTATION_STATION_NAME": "Кухня" }
```

(тот же `YASTATION_STATION_NAME`/`YASTATION_STATION_ID`, что понимает
`quasar.Connect()` — см. REPL/HTTP default-account режим).

После сохранения файла — полный перезапуск Claude Desktop (не просто
новое окно). `-stdio` и обычный HTTP-режим — взаимоисключающие: с флагом
сервер вообще не открывает порт, `YASTATION_HTTP_ADDR`/`_TOKEN` в этом
режиме не участвуют.

### Python-клиент

`clients/python/yastation_client.py` — тонкая обёртка над этим же HTTP
API, без внешних зависимостей (только stdlib, `urllib`/`json`), можно
просто скопировать файл к себе в проект:

```python
from yastation_client import YastationClient

client = YastationClient("http://localhost:8737", server_token="секрет")
client.say("привет с питона")
client.command("/volume 3")

# bring-your-own-token: колонка другого аккаунта
mom = YastationClient("http://localhost:8737", server_token="секрет", yandex_token="мамин x-token")
for station in mom.stations():
    print(station.id, station.name)
mom.say("не забудь лекарство", station="Кухня")
```

Файл рабочий и как самостоятельный пример: `python3 yastation_client.py`
(смотри переменные окружения в шапке файла).

## Деплой на сервер (systemd + Caddy)

```bash
bash scripts/setup_server.sh
```

Полностью интерактивно, sudo не нужен снаружи (вызывается изнутри
только на шаге установки systemd-юнита). Спросит порт (если занят —
сам возьмёт следующий свободный), поддомен для Caddy, путь к файлу
токенов, токен для API (можно сгенерированный по умолчанию, можно
свой), нужно ли подключить `examples/commands.json`. Пользователь для
сервиса берётся автоматически (`whoami`/`$SUDO_USER`) — отдельно
указывать не надо. Дальше: собирает `yastation-server` в `bin/` внутри
репозитория, пишет `.env` в корень репы (права 600), предложит пройти
QR-авторизацию прямо тут же, если токена ещё нет, и предложит
установить systemd-юнит (`/etc/systemd/system/yastation.service`,
`WorkingDirectory`/`EnvironmentFile` — этот же репозиторий и `.env`). В
конце — тестовый `curl` и, если указан поддомен, готовый блок для
Caddyfile.

## Свои команды с параметрами

Помимо встроенных команд можно описать свои в JSON-конфиге —
`/имя параметры` рендерит фразу-шаблон и шлёт её как голосовую команду
или TTS. Пример — `examples/commands.json`:

```json
{
  "commands": [
    {
      "name": "english",
      "aliases": ["en"],
      "help": "Сказать фразу по-английски: /english текст",
      "params": ["text"],
      "template": "Say this exact words in English: \"$text\"",
      "kind": "command"
    },
    {
      "name": "translate",
      "params": ["lang", "text"],
      "template": "Переведи на $lang: $text",
      "kind": "command"
    }
  ]
}
```

Все параметры, кроме последнего, — одно слово; последний забирает весь
остаток строки (можно с пробелами) — так `/english привет как дела`
даёт `$text = "привет как дела"`. `kind` — `"command"` (по умолчанию,
как `/cmd`) или `"say"` (как `/say`).

Подключить:

```bash
yastation -config examples/commands.json
# или через переменную окружения (работает и для yastation-server):
export YASTATION_COMMANDS_FILE=examples/commands.json
```

## Безопасность bring-your-own-token

x-token, который принимает `X-Yandex-Token`, — это токен для Yandex
Passport OAuth уровня всего аккаунта (тот же, что использует официальное
мобильное приложение), а не токен, ограниченный только умным домом.
Дать его чужой программе — по сути дать доступ ко всему аккаунту Яндекса,
это не мелочь вроде пароля от одного сервиса. Практические следствия:

- Передавай `X-Yandex-Token` только по HTTPS (сам этот проект TLS не
  делает — оборачивай через Caddy/nginx, как в примере деплоя выше;
  голый HTTP с чужим токеном в заголовке — утечка чужого аккаунта).
- Не логируй и не сохраняй чужие токены сам — этот проект их не пишет
  на диск, только держит sha256-хэш как ключ 20-минутного кэша в памяти,
  сам токен нигде не логируется.
- Проси токен только у людей, которым доверяешь настолько, что готов
  формально отвечать перед ними за то, что с их аккаунтом ничего плохого
  не случится — семья/друзья, не случайные пользователи из интернета.
- Не строй на этом публичный веб-сервис "пришли токен — поуправляем
  твоей колонкой" для незнакомых людей: даже при благих намерениях это
  будет выглядеть — и по факту являться — точкой, куда можно перехватить
  чужие аккаунты Яндекса целиком, а не только колонку.

## Тесты

```bash
go test ./... -race
```

Вся логика, которая не требует реального аккаунта Яндекса (диспетчер
команд, очередь, планировщик, кодирование id устройства в фразу-триггер,
построение и сериализация payload'ов сценариев с проверкой точной формы
JSON, разбор реалистичного ответа со списком устройств, весь
Glagol-клиент включая полный round-trip через встроенный тестовый
WebSocket-сервер), покрыта тестами. Живой HTTP-вызов к серверам Яндекса
без реального аккаунта не протестировать — но форма отправляемых и
разбираемых JSON-структур зафиксирована golden-тестами, чтобы будущий
рефакторинг случайно не откатил её обратно к неверной.
