# yastation

Неофициальный клиент для управления Яндекс Станцией (Алисой) с
компьютера или сервера: озвучить текст, отправить голосовую команду,
поставить таймер/будильник, дёрнуть сценарий умного дома, запланировать
команды на потом. Не связан с Яндексом и не аффилирован с ним.

**Возможности:**
- REPL и одноразовый запуск команд из shell (cron/systemd timer/алиасы)
- HTTP-бэкенд — управляй колонкой с сервера из любой программы
- Быстрый локальный путь (Glagol WebSocket в локальной сети) с
  автоматическим fallback на облако, если локалка недоступна
- Планировщик (`/every`, `/at`) и скрипты (`/execute файл.txt`)
- Асинхронная очередь команд — не ждёшь round-trip к Яндексу на каждый ввод
- Свои команды с параметрами через конфиг (см. `examples/commands.json`)

**Нужен Go 1.23+** (из-за `github.com/coder/websocket`, единственной
внешней зависимости — используется для быстрого локального протокола
Glagol). Всё остальное — стандартная библиотека.

Официального API у Яндекса для этого нет. Общее понимание протокола
взято из нескольких открытых репозиториев про Яндекс Станцию; сама
реализация написана на Go самостоятельно. Подробности и что именно
проверено на реальном аккаунте — в `PROTOCOL_NOTES.md`. Протокол
недокументирован и может измениться в любой момент без предупреждения.

## Структура

```
cmd/
  yastation/            интерактивный REPL + одноразовый запуск команд из shell
  yastation-auth/       разовая QR-авторизация
  yastation-server/     HTTP-бэкенд — управляй колонкой с сервера из любой программы
internal/
  quasar/                библиотека протокола: сессия, устройства, сценарии, команды
  glagol/                 локальный WebSocket-протокол (быстрый путь, см. ниже)
  queue/                   асинхронная очередь: Enqueue возвращает мгновенно, воркер шлёт по одной по порядку
  scheduler/               /every и /at — периодические и разовые задачи
  dispatch/                 лёгкий диспетчер команд ("/имя аргументы", свой, не func_parser)
  app/                       склеивает всё выше в общий набор команд, разделяемый REPL и HTTP-сервером
examples/
  morning.txt             пример скрипта для /execute
```

## Установка и первый запуск

```bash
go build ./...          # или go run ./cmd/... по отдельности
go run ./cmd/yastation-auth   # один раз: логин по QR-коду
go run ./cmd/yastation         # интерактивный REPL
```

Токены сохраняются в `$YASTATION_TOKEN_FILE` (если задано) или
`<user config dir>/yastation/tokens.json` (на Linux — `~/.config/yastation/tokens.json`)
— не публикуй и не коммить этот файл.

## Одноразовый запуск из командной строки

Не обязательно сидеть в REPL — можно вызвать одну или несколько команд
прямо из shell (удобно для cron, systemd timer, алиасов):

```bash
yastation "привет с компа"                      # одна фраза, потом выход
yastation -c "/volume 3" -c "/say доброе утро"     # несколько команд подряд
yastation -e examples/morning.txt                 # то же, что -c "/execute ..."
yastation -c "/every 30m /say вода" -i             # запланировать и остаться в REPL
```

Код возврата процесса — `1`, если хоть одна из команд упала с ошибкой (для
скриптов/cron), `0` если всё прошло гладко.

## Быстрый путь: локальный Glagol вместо облака

По умолчанию команды идут через облако Яндекса (создать/поправить
служебный сценарий, потом дёрнуть его) — это надёжно работает из любой
сети, но занимает ~1-2 секунды на команду. Если комп и колонка в одной
локальной сети, можно включить прямое WebSocket-подключение к колонке
(Glagol) — обычно это заметно быстрее.

Нужен только IP:порт колонки в локальной сети (у Яндекса нет надёжного
способа найти его без mDNS-библиотеки, поэтому просто задай вручную —
посмотри в списке DHCP-клиентов роутера или в приложении Дом с Алисой):

```bash
export YASTATION_GLAGOL_HOSTS="abc123deviceid=192.168.1.42:1961"
# несколько колонок через запятую:
# YASTATION_GLAGOL_HOSTS="dev1=192.168.1.42:1961,dev2=192.168.1.43:1961"
```

Device id колонки видно в выводе `/stations`. Если хост для устройства не
задан или подключение/отправка не удались — команда автоматически
падает обратно на облачный путь, ничего вручную переключать не надо.
Учти: у Glagol в этой реализации только один вид команды (`sendText`, как
если бы фразу произнесли голосом) — TTS-режим `/say` через Glagol технически
шлётся так же, как `/cmd`, разницы между ними локально нет (см.
`PROTOCOL_NOTES.md`).

## REPL

```
> привет с компа!               # просто текст -> озвучивается станцией
> - какая погода                  # дефис-пробел -> голосовая команда (алиас /cmd)
> /volume 3                      # громкость 0..10
> /say выключи свет
> /ask чё делаешь                 # алиас /cmd — ответ прозвучит из колонки, не в терминал
> /notify задача выполнена volume=4
> /timer 10 проверить духовку
> /alarm 7:30
> /reminder завтра купить хлеб
> /play  /pause  /stop  /next  /prev
> /weather
> /news
> /scenarios
> /scenario Вечер
> /stations                       # диагностика
> /every 30m /say выпей воды        # периодическая команда: s/m/h
> /at 7:30 /say доброе утро          # разовая команда в HH:MM
> /schedules
> /unschedule_all
> /execute examples/morning.txt      # прогнать скрипт построчно
> /help
```

Чтобы указать конкретную колонку вместо той, что задана переменными
окружения по умолчанию, добавь `station=Имя` в любое место аргументов:
`/say station=Кухня привет`.

## Асинхронность и очередь команд

Каждая команда станции — это несколько HTTP-запросов к Яндексу (создать
или поправить сценарий, затем дёрнуть его), и в сумме это может занимать
секунду-две. Чтобы не блокировать вызывающий код, `internal/queue`
устроен так:

- `App.Enqueue(line)` кладёт команду в очередь и **сразу возвращает
  управление**, ничего не дожидаясь. Ей пользуется REPL и планировщик —
  ты печатаешь следующую команду, не дожидаясь пока предыдущая долетит до
  колонки.
- Один воркер-горутина разбирает очередь строго по порядку, так что две
  команды, отправленные подряд, дойдут до колонки в том же порядке, а не
  наперегонки.
- `App.Execute(ctx, line)` — та же очередь, но ждёт реального результата
  и возвращает его вызывающему; этим пользуется HTTP-бэкенд, потому что
  HTTP-ответ должен нести реальный статус (успех/ошибка), но при этом
  конкурентные запросы всё равно не гонятся друг с другом за один и тот
  же сценарий колонки.

## HTTP-бэкенд (cmd/yastation-server)

Чтобы слать команды на Алису с сервера из любой программы (curl, другой
скрипт, вебхук и т.п.), а не только из интерактивного REPL:

```bash
export YASTATION_HTTP_TOKEN=секрет   # опционально, но нужен если сервер смотрит наружу
go run ./cmd/yastation-server
```

По умолчанию слушает `:8737` (задаётся `YASTATION_HTTP_ADDR`).

```bash
curl -X POST localhost:8737/command \
  -H "Authorization: Bearer $YASTATION_HTTP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"text": "привет с сервера"}'

curl -X POST localhost:8737/command \
  -H "Authorization: Bearer $YASTATION_HTTP_TOKEN" \
  -d '{"line": "/volume 3"}'

curl localhost:8737/schedules -H "Authorization: Bearer $YASTATION_HTTP_TOKEN"
curl localhost:8737/healthz   # без авторизации, для мониторинга
```

Тело запроса `/command`:
- `{"line": "/say привет"}` — полная команда, как в REPL;
- `{"text": "привет", "station": "Кухня"}` — короткая форма, TTS;
- `{"text": "включи радио", "as_command": true}` — короткая форма, как
  голосовая команда (`/cmd`), а не TTS.

Ответ: `{"ok": true, "output": "..."}` либо `{"ok": false, "error": "..."}`.

Каждый запрос ждёт реального выполнения (через ту же очередь, что и
REPL), так что можно сразу проверять `ok` в ответе.

## Если станций несколько

По умолчанию берётся первая найденная. Задай явно через переменные
окружения:

```
YASTATION_STATION_ID=айди_станции
# или
YASTATION_STATION_NAME=Кухня
```

## Тесты

```bash
go test ./... -race
```

Вся логика, которая не требует реального аккаунта Яндекса (диспетчер
команд, очередь, планировщик, кодирование id устройства в фразу-триггер,
построение и сериализация payload'ов сценариев с проверкой точной формы
JSON, разбор реалистичного ответа со списком устройств, весь
Glagol-клиент включая полный round-trip через встроенный тестовый
WebSocket-сервер), покрыта тестами. Живой HTTP-вызов к серверам Яндекса
без реального аккаунта не протестировать — но форма отправляемых и
разбираемых JSON-структур зафиксирована golden-тестами, чтобы будущий
рефакторинг случайно не откатил её обратно к неверной.
