# Протокол: что точно, а что реконструкция

Яндекс не публикует официальный API для управления Станцией с компа —
всё, что тут написано, реконструировано по общедоступным знаниям о том,
как это устроено (в духе разборов, на которые ссылался и старый
Python-прототип), а не скопировано из чужого исходного кода. Часть вещей
я уверен что верны, часть — лучшая догадка, которую надо перепроверить на
реальном аккаунте при первом запуске.

## Уверенно верно (это устоявшийся, много раз описанный протокол)

- **QR-логин**: `passport.yandex.ru/pwl-yandex` -> CSRF из HTML ->
  `.../api/passport/auth/password/submit` -> `.../auth/magic/code` даёт
  `link` для QR -> поллинг `.../auth/magic/code/status` до
  `state == "otp_auth_finished"` -> `.../sessions/get_session` закрепляет
  сессионные куки.
- **Куки -> OAuth x-token**: `POST
  https://mobileproxy.passport.yandex.net/1/bundle/oauth/token_by_sessionid`
  с `client_id`/`client_secret` (это публичные ID мобильного клиента
  Яндекса, используются повсеместно в открытых проектах для того же
  API, не секрет конкретного аккаунта) и заголовками
  `Ya-Client-Host`/`Ya-Client-Cookie`.
- **Проверка токена**: `GET
  https://mobileproxy.passport.yandex.net/1/bundle/account/short_info/`
  с `Authorization: OAuth <x_token>`.
- **CSRF для iot.quasar.yandex.ru**: нужно сначала `GET
  https://yandex.ru/quasar`, вытащить `"csrfToken2":"..."` из HTML,
  слать заголовком `x-csrf-token` на все не-GET запросы. При 403 токен
  протух — взять заново.
- **Список устройств**: `GET
  https://iot.quasar.yandex.ru/m/v3/user/devices`, структура
  households -> rooms -> devices, у колонок есть `quasar_info` с
  `device_id`/`platform`.
- **Список сценариев**: `GET
  https://iot.quasar.yandex.ru/m/user/scenarios`, создание/правка —
  `POST`/`PUT .../m/v4/user/scenarios[/{id}]`, ручной запуск без
  произнесения фразы — `POST .../m/user/scenarios/{id}/actions`.

## Реконструкция, требует проверки на реальном аккаунте

Это касается `buildTTSScenario`/`buildCommandScenario` в
`internal/quasar/devices.go` — точная форма JSON тела сценария (какие
именно поля внутри `capabilities`/`state`, какая ровно `instance` у
`devices.capabilities.quasar.server_action` для TTS против обычной
голосовой команды) я реконструировал по смыслу протокола Quasar
(смарт-девайсы получают команды через `capabilities`/`state` с
`instance`+`value`), но **не проверял на живом аккаунте** — своего
Яндекс-аккаунта с колонкой у меня, понятно, нет.

Если `/say` или `/cmd` падают с ошибкой от Яндекса (не с ошибкой сети, а
с осмысленным ответом типа "invalid request" или похожим) — вот что
проверить в первую очередь:

1. Залогинься через `go run ./cmd/yastation-auth`, потом руками сделай
   `GET https://iot.quasar.yandex.ru/m/user/scenarios` тем же клиентом
   (можно временно добавить debug-принт тела ответа в `loadScenarios`) и
   посмотри на форму существующего у тебя вручную созданного голосового
   сценария в приложении Дом с Алисой — по нему видно точные имена
   полей.
2. Скорее всего расхождение будет именно в
   `ScenarioCapability`/`ScenarioCapabilityState` — возможно, нужен
   другой `type` капабилити или `instance`, либо `value` должно быть не
   голой строкой, а объектом `{"phrase": "..."}` / похожей обёрткой.
3. `encodeDeviceTrigger` (маска hex -> кириллица) — это моя придумка для
   получения уникальной, практически непроизносимой фразы-триггера на
   устройство; при желании эту функцию можно упростить или заменить на
   что угодно детерминированное — формат фразы Яндексу, скорее всего,
   не важен, лишь бы она была уникальна в рамках аккаунта.

Всё остальное (очередь, планировщик, диспетчер команд, HTTP-сервер)
никак не завязано на эти детали и тестами покрыто полностью — поправить
нужно будет только тело сценария в `devices.go`, если что-то не так.
